# Literature Multi-Agent Collaboration Workflow

`created: 2026-05-03 | status: active | version: v1.0`

> 多 Agent 协作的文献检索与验证工作流。按需加载，持续迭代。

---

## Trigger

超哥发起文献/资料调研类任务时，默认执行此工作流。无需重复说明。

---

## Step 0: Task Scoping（搜前对齐）

**目的：在开始搜索前确定边界，避免三路 Agent 各自为政。**

超哥给出任务后，我先按以下模板确认：

```
任务理解：
- 主题：[确认]
- 场景：[查最新进展 / 验证结论可靠性 / 入门新方向 / 其他]
- 时间范围：[最近N年 / 不限]
- 文献类型：[综述为主 / 原创为主 / 混合]
- 最低引用数：[有要求 / 不限]
- 侧重方向：[应用 / 机理 / 两者都要]
- 你已有的信息：[如果有，简单描述]
```

超哥只需确认或修改，不需要逐条回答。快的 10 秒搞定。

> **场景决定后续策略：**
> - 查最新 → 偏 arXiv + 最近 1-2 年，快跑快出
> - 验证结论 → 偏多源交叉 + 高引，深度验证
> - 入新方向 → 偏综述 + 高引综述，先建框架

---

## Step 1: Parallel Retrieval（并行检索）

启动 3 个独立 Agent，各搜各的：

| Agent | Source | Focus |
|-------|--------|-------|
| A | Semantic Scholar MCP | 论文搜索、引用网络、作者追踪 |
| B | arXiv MCP | 最新预印本（cond-mat, mtrl-sci） |
| C | WebSearch / WebFetch | 通用检索（中文源、技术文档、官方信息、交叉验证） |

> 所有来源 **并发执行**，不做优先级取舍。

**新增：Quality Gate（搜索质量自查）**
每个 Agent 返回结果后，自查以下内容：
- 是否返回 ≥ 设定数量（默认 5 条以上）？若不足 → 标记并考虑补搜
- 结果与 Step 0 对齐的主题是否明显相关？若偏题 → 标记并调整查询词
- MCP/API 是否有超时或报错？若有 → 在 Phase 2 中标注该源不可用

自查结果随数据一起进入 Phase 2。

---

## Step 2: Cross-Verification & Adjudication（交叉验证与裁决）

启动独立验证 Agent，汇总三路数据。

### 裁决规则

当多源结论存在分歧时，按以下优先级判断：

| 优先级 | 准则 | 说明 |
|--------|------|------|
| 1 | **多源一致 > 单源** | 两个以上独立来源支持同一结论 → 采信 |
| 2 | **时效优先** | 同年文献 → 更高引优先；跨年 → 更新的优先 |
| 3 | **综述权重** | 系统综述/荟萃分析 > 单篇原创 > 预印本 |
| 4 | **源可用性标记** | 若某源在 Quality Gate 中标记为不可用，自动降权 |
| 5 | **存疑标记** | 以上无法裁决 → 标记为`争议`，等 Step 5 问超哥 |

### 输出结构

每条结论带三个标签：

| 标签 | 含义 |
|------|------|
| `Confidence: 高/中/低` | 可信度（基于多源一致性和源权威性） |
| `Consensus: 一致/分歧` | 多源是否同意 |
| `Sourced: A+B, A+C, ...` | 哪些来源支持 |

---

## Step 3: Relevance Assessment（匹配度评估）

对照 Step 0 确定的需求，逐条评估：

- 每条结论与需求的匹配度（%）
- 部分匹配 → 说明缺口在哪里
- 是否需要补充检索

> 此阶段如果频繁出现"不匹配"，说明 Step 0 的边界可能与实际需求有偏差 → 主动问超哥是否需要调整方向。

---

## Step 4: Output（结果输出）

### 格式

```markdown
# YYYY-MM-DD: Topic Name
`tags: #tag1 #tag2 | workflow: v1.0 | task: 查最新/验证/入门`

## Summary
一句话核心结论。

## Results
| # | Source | Finding | Confidence | Match | Note |
|---|--------|---------|------------|-------|------|
| 1 | SS+Web | ... | 高 | 90% | 多源一致 |
| 2 | arXiv | ... | 中 | 60% | 仅单源 |

## Cross-Validation
- ✅ A 和 B 在 X 点上结论一致
- ⚠️ C 在 Y 点上与 A/B 矛盾（已按裁决规则取 A/B）
- 🔴 Z 源 Quality Gate 标记不可用，未参与

## Context Gaps
- [如需补充实验条件/数据背景]

## Next Steps
- 推荐下一步方向/需要超哥补充的信息
```

### 文件落地

| 输出 | 路径 | 内容 |
|------|------|------|
| 完整报告 | `archive/outputs/YYYY-MM-DD_Topic.md` | 含 Step 1-4 全量内容 |
| 精炼结论 | `archive/topics/Research-Notes.md` | 仅核心结论、模型、空白 |

## Step 5: Human Review & Redirect（人工审查与转向）

**这是 HITL（Human-in-the-Loop）的关键环节。**

输出结果后，问超哥一个问题（不是一堆）：

> "超哥，以上结果看下来，下一步是：
> (a) 基于这个结果深挖某个子方向
> (b) 方向不对，换一个角度重搜
> (c) 直接整理成文稿/提案
> (d) 补充你那边实验条件/数据，我重做匹配"

超哥答复后，按指令走。如果是 (b)，不用从头跑——保留已搜到的高质量文献，只在 Step 1 换查询词重新过滤。

## Cross-Cutting: Context Gap Callout（背景补充）

**适用于所有阶段。** 

### 触发原则

1. **先自查，再问超哥** — 遇到不懂的设备名/方法/指标，先 WebSearch 查一轮
2. **自查仍不确定 → 问超哥** — 问题要有针对性，限 1 条消息问完
3. **不问"你咋想"** — 只问事实性问题（"你们有 X 设备吗？"），不问开放性问题

### 典型触发场景

| 场景 | 怎么做 |
|------|--------|
| 论文方法超哥可能没设备 | 先搜该方法的普及度，如果很冷门再问 |
| 需要数据细节来判断匹配 | 直接问数据来源和规模 |
| 发现超哥实验室可用但未用的方法 | 先搜该方法在超哥方向的应用实例，再推荐 |
| 有缺口但不知选哪个 | 给两个选项 + 各自的优劣分析，让超哥选 |

## Adjudication Reference Table

当交叉验证遇到冲突时，按此表处理：

| 冲突类型 | 处理方式 |
|----------|----------|
| 结论 A 与 B 矛盾，A 多源支持 | 采信 A，标注 B 为少数派 |
| 结论 A 与 B 矛盾，均为单源 | 降级两者置信度为`低`，标记`争议` |
| A 来源挂了（Quality Gate） | A 不参与验证，标注 A 不可用 |
| 所有来源均不支持结论 | 标记为`推测`，明确告知超哥无直接证据 |
| 结论随时间变化（旧说有害，新说无害） | 按时效优先，标注时间线 |
